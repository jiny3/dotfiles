# 全局 AGENTS.md 编写最佳实践

## 目标

全局 `AGENTS.md` 是给所有编码代理读取的长期工作协议，适合放**跨项目稳定成立的偏好、流程、质量标准和安全边界**。

一句话规则：

> 全局 `AGENTS.md` 应该短、稳定、可执行、可验证、跨项目适用；项目细节下沉到项目级 `AGENTS.md`，复杂流程沉淀为 Skill，硬性安全交给配置和权限系统。

## 适用范围

本文适用于：

- 用户级全局说明，例如 `~/.codex/AGENTS.md`、`~/.pi/agent/AGENTS.md`；
- 组织或机器级默认 agent 行为规范；
- 需要跨仓库复用的编码代理工作约定。

不适用于：

- 某个仓库的构建、测试、发布命令；
- 某个子系统的架构说明；
- 特定外部系统的长流程操作手册；
- 密钥、token、账号、生产凭证等敏感信息。

## 核心原则

### 1. 只放“每次都值得提醒”的规则

全局文件会进入代理上下文，过长会浪费上下文并稀释重点。

适合放：

- 默认语言和回复风格；
- 通用工作方式；
- 编码质量标准；
- 调试和验证策略；
- 安全边界；
- 最终回复格式。

不适合放：

- 单个项目的 `pnpm test`、`make build` 等命令；
- 某个目录的模块说明；
- 大段 README、API 文档、会议纪要；
- 罕见任务流程；
- 任何秘密或私有数据。

### 2. 写行为，不写口号

差的写法：

```md
- 写高质量代码。
- 注意安全。
- 尽量测试。
```

好的写法：

```md
- 修改前先阅读相关文件和已有测试。
- 改完优先运行与改动最相关的测试；无法运行时说明原因。
- 不新增生产依赖，除非用户明确同意。
- 不吞异常，不用静默 fallback 掩盖真实错误。
```

每条规则最好能回答：

> 代理应该具体做什么？如何判断它做到了？

### 3. 保持优先级清晰

避免互相冲突的规则，例如：

```md
- 总是快速完成。
- 总是完整验证。
- 不要问问题。
- 不确定时必须问问题。
```

推荐明确优先级：

```md
- 优先保证正确性，其次是速度。
- 低风险细节可合理假设并继续。
- 涉及破坏性操作、权限、安全、生产环境时必须先确认。
```

### 4. 全局、项目、子目录分层治理

推荐分层：

| 层级 | 放什么 | 示例 |
|---|---|---|
| 全局 `AGENTS.md` | 跨项目工作协议 | 默认中文、先读后改、验证优先、安全确认 |
| 项目根 `AGENTS.md` | 仓库级规则 | 安装命令、测试命令、目录结构、贡献流程 |
| 子目录 `AGENTS.md` | 局部规则 | frontend/backend/infra 的专属命令和限制 |
| Skill | 特定任务流程 | 发布流程、飞书操作、复杂排查 SOP |
| 配置/权限 | 强安全约束 | sandbox、approval、禁止危险命令、CI gate |

越靠近工作目录的规则越具体，可细化或覆盖上层规则。全局规则不要污染项目规则。

### 5. 规则要可验证

优秀规则通常带有可观察结果：

- 运行了哪些测试；
- 修改了哪些文件；
- 是否说明无法验证的原因；
- 是否列出剩余风险；
- 是否没有执行需要确认的危险操作。

避免把“完成”定义成感觉，例如“看起来没问题”。

## 推荐结构

全局 `AGENTS.md` 建议使用稳定标题，便于代理识别：

```md
# Global Agent Rules

## Language

## Working Style

## Coding Standards

## Debug Policy

## Execution Rules

## Validation

## Safety

## Final Response
```

## 推荐模板

```md
# Global Agent Rules

## Language

- 默认用简体中文回复；用户明确指定时再切换语言。

## Working Style

- 先给结论或结果，再补必要上下文。
- 像高绩效资深工程师一样工作：直接、克制、执行优先。
- 能合理假设就继续，不为低风险细节反复确认。
- 不加无关功能，不做顺手重构，不给泛泛建议代替落地执行。
- 优先选择简单、可维护、可上线的方案。

## Coding Standards

- 写低复杂度代码，保证易读、易调试、易修改。
- 避免过度设计、重抽象、额外分层、大依赖、炫技写法和隐式行为。
- 保持 API 小而清晰，行为显式，命名明确，控制流平坦，优先早返回。
- 注释只解释意图、边界和取舍，不复述代码字面意思。

## Debug Policy

- 先追根因，不做只压症状的补丁。
- 让错误显式暴露；不要靠静默兜底、伪成功、吞异常或隐藏默认值掩盖问题。
- 如果问题来自重复逻辑、双重真值、共享状态或跨模块行为，按结构性问题处理，不叠补丁。

## Execution Rules

- 多步任务在调用工具前，先用 1 到 2 句说明要做什么和第一步。
- 先读相关文件和真实上下文，再修改。
- 改动保持最小闭环，但该删的死代码、冗余分支和重复逻辑要一起清掉。
- 有匹配的 Skill 就先读取 `SKILL.md` 并按它执行。

## Validation

- 改完先做最相关的验证：优先针对性测试，再类型检查 / lint / build，最后最小冒烟。
- 能跑就跑；不能跑就明确说明原因。
- 不把静态阅读包装成运行时验证。

## Safety

- 未经确认，不执行破坏性操作：删除数据、重置历史、强推、生产部署、修改生产配置。
- 新增生产依赖、改变鉴权/权限、迁移数据结构前，先说明影响并征求确认。
- 不读取、输出或保存密钥、token、密码、个人隐私和生产凭证。

## Final Response

- 先给结论。
- 如果修改了文件，列出关键文件路径和改动摘要。
- 列出已运行的验证命令和结果。
- 明确说明未验证项、失败项和剩余风险。
```

## 写作规范

### 使用祈使句和短句

推荐：

```md
- 修改前先阅读相关文件。
- 改完运行最相关测试。
```

避免：

```md
- 我希望你在大多数情况下尽量考虑先了解一下项目背景，如果方便的话也可以适当测试。
```

### 一条规则只表达一个约束

推荐：

```md
- 新增生产依赖前先征求确认。
- 无法运行测试时说明原因。
```

避免：

```md
- 新增依赖、跑测试、写文档、处理错误、提交代码都要谨慎。
```

### 用“必须 / 不要 / 优先 / 除非”明确边界

推荐：

```md
- 必须先读真实上下文再修改。
- 不要吞异常或返回伪成功。
- 优先运行针对性测试。
- 除非用户明确要求，不做无关重构。
```

### 保留人工介入出口

推荐：

```md
- 如果连续两次验证失败，停止叠补丁，重新分析根因。
- 如果缺少关键业务信息，提出最小必要问题。
- 如果需求和现有约束冲突，先指出冲突再继续。
```

## 常见反模式

### 反模式 1：把项目命令放进全局文件

不推荐：

```md
- 每次改完运行 `pnpm test`。
```

如果并非所有项目都用 pnpm，应改为：

```md
- 改完运行项目中最相关的测试；具体命令以项目 `AGENTS.md`、README 或脚本配置为准。
```

### 反模式 2：复制大段文档

不推荐：

```md
- 以下是完整 API 文档：...
```

推荐：

```md
- 需要 API 细节时，优先查阅项目 `docs/api.md`。
```

### 反模式 3：用自然语言替代安全控制

不推荐只写：

```md
- 不要执行危险命令。
```

更好的组合：

- 在 `AGENTS.md` 写清安全边界；
- 在工具或运行环境中配置 sandbox、approval、权限限制；
- 在 CI/CD 中设置强制 gate。

### 反模式 4：规则过多且互相覆盖

不推荐维护几百行全局规则。过长文件会导致：

- 关键规则被淹没；
- 上下文浪费；
- 规则冲突；
- 维护成本升高。

建议：

- 全局只保留跨项目高频规则；
- 项目细节放项目级文件；
- 复杂流程做 Skill；
- 过时规则及时删除。

## 维护机制

### 何时更新全局 AGENTS.md

当出现以下情况时，考虑更新：

- 代理重复犯同一类错误；
- 你连续多次给出相同反馈；
- 某条工作偏好在所有项目中都适用；
- 新增了必须长期遵守的安全边界；
- 现有规则过时或造成误导。

判断标准：

> 如果同一条反馈已经说过两次，就值得考虑沉淀为规则。

### 更新流程

1. 先判断规则是否真的跨项目适用。
2. 用一句可执行短句表达。
3. 放到最合适的小节。
4. 删除或合并冲突旧规则。
5. 用一次真实任务验证代理是否能遵守。

### 定期审查

建议每季度或每次重大工作流变化后检查：

- 是否有项目专属规则误放在全局；
- 是否有过时命令或工具；
- 是否有重复、冲突、空泛的规则；
- 是否可以下沉到项目级 `AGENTS.md` 或 Skill。

## 检查清单

新增或修改全局 `AGENTS.md` 前，逐项检查：

- [ ] 这条规则是否跨多数项目都适用？
- [ ] 是否每次会话都值得加载？
- [ ] 是否能转化为明确行为？
- [ ] 是否避免了项目专属命令和路径？
- [ ] 是否没有包含秘密或私有数据？
- [ ] 是否没有和现有规则冲突？
- [ ] 是否能被项目级规则自然细化或覆盖？
- [ ] 是否比放到 Skill / README / 配置文件更合适？

## 最小结论

优秀的全局 `AGENTS.md` 应满足：

> 短而稳定，跨项目适用；写行为不写口号；写边界不写秘密；写验证不写感觉；项目细节下沉，复杂流程技能化，硬性安全交给工具配置。
